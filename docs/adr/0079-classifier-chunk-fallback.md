# 0079. 분류기 폴백은 10건 묶음 단위로, Claude 분류기도 묶음으로 부른다

- 상태: 채택
- 날짜: 2026-11-26
- 결정한 사람: 선웅제(배치 C59 지시: 묶음 단위 폴백, Claude 묶음 호출, 깨진 묶음은 단건으로, 이름 섞임은 한계로 둠)
- 관련: [ADR 0048](0048-gemini-classifier-replaces-jev.md)(Gemini 기본·자동 대체), [ADR 0003](0003-classifier-jev-and-claude.md), devlog [C59](../devlog/2026-11-26-batch-C59.md)

## 배경

운영 로그(`~/.nsm/logs/nsm.log`)를 보면 11-20~11-26 매일 새벽 00:30~01:00 수집 때 `gemini-3.5-flash-lite`가 HTTP 503(high demand)을 냈다. 재시도(20·40·60초)로 넘어간 날도 있고(11-21~23), 끝내 실패해 Claude로 대체된 날도 있다(11-20, 24, 25, 26).

11-24에는 00:54:51~00:58:24 구체 사실 판정(`classify_facts`) 묶음이 503 네 번으로 실패해 Claude로 넘어갔다. Claude는 23건을 단건으로 23번 불렀다(00:58:28~00:58:58, 30초). 이어 01:00 원고 만들기의 같은 소식 판정도 Claude 단건 16번이었다. 수집 잡이 길었던 주원인은 Gemini 재시도 대기(약 6분)와 원문 읽기다. Claude 호출은 30초였다.

그래서 이 결정의 목적은 시간 단축이 아니다. 호출 수·비용을 정리하고 폴백을 정확하게 만드는 것이다. 코드에서 두 가지가 걸렸다.

1. `FallbackClassifier.classify_many`가 `texts` 전체를 한 번에 넘겼다. `GeminiClassifier`는 10건(`BATCH`)씩 처리한다. 그래서 앞 묶음이 성공하고 뒤 묶음에서 실패하면 성공한 결과를 버리고 전체를 Claude로 다시 보낼 수 있었다.
2. `ClaudeClassifier.classify_many`는 단건 `classify`를 건수만큼 직렬로 불렀다. 시스템 문구와 지시문 토큰이 건마다 되풀이됐다.

## 선택지

1. **그대로 둔다**: 바꿀 것이 없다 / 뒤 묶음 실패 때 이미 받은 판정을 버리고, Claude 호출이 건수만큼 나간다.
2. **폴백만 묶음 단위로**: 판정을 버리지 않는다 / Claude 단건 호출 수는 그대로다.
3. **폴백 묶음 단위 + Claude 묶음 호출(채택)**: 둘 다 해결된다 / 묶음 응답 모양이 깨질 수 있어 그때의 처리가 필요하다.

## 결정

3을 골랐다.

- `FallbackClassifier.classify_many`는 `texts`를 `CHUNK = 10`건씩 잘라 묶음마다 `_call("classify_many", …)`을 부르고 이어 붙인다. 빈 목록이면 호출하지 않는다.
  - `CHUNK`는 `gemini.BATCH`와 같은 값이다. 순환 import를 피하려고 가져오지 않고, 두 값이 같은지는 테스트로 고정한다.
  - 넘어가는 규칙(`ChainState`, 30분 뒤 첫 분류기 재시도, 6시간 알림)은 그대로다. 묶음 하나가 실패하면 그 묶음부터 다음 분류기가 받고, 남은 묶음도 넘어간 분류기로 간다.
- `ClaudeClassifier.classify_many`
  - 0건은 `[]`이고, 1건은 기존 단건 `classify`다.
  - 2건 이상은 10건씩 묶어 `messages.create`를 한 번 부른다. 번호를 매긴 나열이고 건당 1500자다(단건은 6000자 그대로).
  - 스키마는 `{"items": [{"i", "label", "confidence"}]}`다. 모든 object에 `additionalProperties: false`를 걸고, 원소는 셋 다 필수다.
  - `max_tokens=2048`, thinking 끔, effort low다. 비용은 묶음마다 `classify_many`로 기록한다.
- 번호 `0..n-1`이 다 있고 라벨이 허용 목록 안이면 번호 순서대로 매핑한다. 신뢰도는 0~1로 자른다.
- **묶음 응답이 깨지면 그 묶음만 단건으로 다시 판정한다.** 깨진 경우는 JSON 파싱 실패, 번호 누락·중복·정수가 아님, 허용되지 않은 라벨, 텍스트 블록 없음이다. 이때는 예외를 던지지 않고 경고 로그를 한 줄 남긴다.
  - 이유: `FallbackClassifier`는 예외를 받으면 다음 분류기(낱말 규칙)로 넘어간다. 그러면 30분 동안 관련성·주제·댓글 세 분류기가 전부 낱말 규칙으로 돈다. 응답 형식이 한 번 깨진 것 때문에 그렇게 되면 안 된다.
  - API 자체 장애와 `stop_reason`이 refusal·max_tokens인 경우는 단건과 같이 예외로 올린다. 다음 분류기로 넘어가는 게 맞는 경우라서다.

## 결과

- Claude로 넘어간 날의 호출 수가 줄어든다. 11-24 기준으로 23번이 3번, 16번이 2번이 된다(단, 응답이 깨진 묶음은 단건 호출이 더해진다). 시스템 문구와 지시문은 묶음마다 한 번만 보낸다.
- 뒤 묶음에서 Gemini가 실패해도 앞 묶음의 판정은 남는다.
- 묶음 호출은 건당 1500자만 보낸다. Gemini 묶음과 같은 길이이고 ADR 0048 비교에서 판정에 충분했다. 단건(1건만 남은 경우)은 6000자 그대로다.
- **알려진 한계(기록되는 분류기 이름이 섞임)**
  - `engine/collect.py`는 `classify_many`가 끝난 뒤 `FallbackClassifier.name`을 읽어 분류 기록의 `who`를 적는다.
  - 그래서 앞 묶음을 gemini가 판정했어도 뒤 묶음에서 넘어가면 그 호출의 결과가 전부 `claude`로 적힌다.
  - 판정 결과는 정확하고 이름만 섞인다. 다만 마지막 실제 분류기(Claude)까지 뒤 묶음에서 실패하면 그 뒤 묶음은 낱말 규칙이 판정한다. 그래도 C59 전과 같은 일이다(그때는 호출 전체가 낱말 규칙으로 갔다). `_judge_facts`처럼 호출 전에 낱말 규칙인지 보는 곳은 호출 도중 넘어간 것을 알아채지 못한다. 이번에는 고치지 않는다. 고치려면 묶음별 판정자를 돌려주는 방식이 필요한데, 그러면 포트 모양이 바뀐다(`nsm/ports/` 동결).
- 그대로 둔 것(배치 지시대로)
  - 묶음 `stop_reason`이 max_tokens면 단건과 같이 예외를 올린다. 10건 응답은 수백 토큰이라 2048에 닿는 일은 드물다고 봤다.
  - 단건으로 다시 판정하는 중 한 건이 예외를 내면 그 묶음 전체가 예외가 된다(단건 `classify`의 API 장애·refusal은 그대로 올리는 규칙).
  - 11건처럼 마지막 묶음이 1건이면 단건 경로(6000자)로 간다.
- 다시 볼 조건
  - 묶음 max_tokens 예외가 로그에 보이면 단건 재시도 경로로 옮긴다.
  - Claude 묶음 응답이 깨졌다는 경고("Claude 묶음 분류 응답이 깨짐")가 자주 나오면 묶음 크기를 줄이거나 지시문을 다듬는다.
  - 분류기별 정확도를 `who`로 비교해야 할 일이 생기면 이름 섞임을 고친다.
