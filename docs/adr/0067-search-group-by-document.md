# 0067. 문서 질문 검색 결과는 문서 단위로 묶어 같은 원고·같은 수집 기사·같은 문서 파일이 상위 k에 한 자리(`rag.per_doc` 기본 1)만 차지하고, 우리 글 근거에는 게시된 글 주소를 보여 줄 때 붙인다

- 상태: 제안
- 날짜: 2026-11-12
- 결정한 사람: 선웅제(배치 R4d 요청), 기본값은 측정 규칙대로 Claude가 고름
- 관련: [ADR 0057](0057-rag-search-and-index-job.md)(검색, 기준값 0.65), [ADR 0065](0065-collected-and-posts-sources.md)(출처, 개정 1·2), devlog [2026-11-12-batch-R4d](../devlog/2026-11-12-batch-R4d.md), R4c devlog "다음 배치 메모"

## 배경

- R4c로 카드 문구 두 벌은 없앴다. 그래도 R4b·R4c 측정에서 상위 5자리를 같은 것이 여러 번 차지했다.
  - 같은 원고의 인스타 캡션과 스레드 글(본문 두 벌), 그리고 같은 원고의 카드 문서.
  - 같은 수집 기사의 여러 조각(기사 하나가 500자 조각 여럿으로 쪼개짐).
  - 같은 문서 파일의 여러 절(ADR·devlog 하나가 상위 5개 중 서너 자리).
- 본문 두 벌은 플랫폼마다 글이 실제로 달라 색인에서 합칠 수 없다(ADR 0065 개정 2). 그래서 검색 단계에서 묶는다.
- 자리를 같은 문서가 나눠 가지면 다른 근거가 밀려난다. 질문 1번은 노린 수집 기사가 R4c에서도 4등이었다.
- R4c의 카드 문서(`posts/<content_id>/cards`)에는 주소·날짜 줄이 없다. 근거로 뜨면 어느 글인지 열어 볼 길이 없다.

## 선택지

1. **검색에서 문서 단위로 묶기(묶음마다 최대 n자리)**: 색인·임베딩은 그대로이고 자리만 바뀐다. 점수가 낮은 다른 문서가 올라온다. 대신 한 문서의 두 번째 조각(긴 문서의 다른 절)은 근거에서 빠질 수 있다.
2. **출처별 상위 n개(ADR 0065 "다시 볼 조건")**: 출처끼리 자리를 나눈다. 같은 출처 안의 중복(같은 기사 여러 조각)은 그대로다.
3. **색인에서 합치기**: 본문 두 벌은 글이 달라 합칠 수 없고, 기사 하나를 조각 하나로 하면 조각이 너무 길어진다(ADR 0056 조각 500자).
4. **글 주소를 색인 본문에 넣기**: 카드 문서에 주소 줄을 넣으면 chunker가 제목 절을 따로 조각내고(ADR 0065 개정 2), 주소가 바뀌면 다시 임베딩해야 한다.

## 결정

**선택지 1. 그리고 글 주소는 보여 줄 때 DB에서 붙인다.**

### 묶기

- 묶음 키: `nsm/rag/search.group_key(path, source_kind)`
  - 우리 글 `posts/<content_id>/…` → `posts/<content_id>`. 플랫폼 문서와 카드 문서가 한 원고다.
  - 수집 자료 `source_items/<id>`, 문서 파일 경로는 경로 그대로(파일 하나가 한 묶음).
- SQL은 후보를 넉넉히(k의 4배, 최소 20개) 가져온다. 파이썬에서 점수 순으로 훑으며 묶음마다 최대 `per_doc`개까지 받아 k개를 채운다(`group_hits`). 후보가 모자라면 있는 만큼.
- `SearchResult.candidates`(측정용 상위 k)와 `hits`(기준값 넘은 것)는 묶은 뒤 기준이다. `top_score`는 묶기 전 1등 점수다(묶어도 1등은 같다).
- 설정 `rag.per_doc`(1~5). 화면 질문(`budgeted_search`)과 검색 측정(`run_eval`)이 같은 값을 쓴다. `search(per_doc=None)`은 묶지 않는다(테스트·직접 호출).

### 기본값 1(측정 규칙)

배치 요청의 규칙: 정답 순위가 떨어지는 질문이 하나라도 있으면 2, 없으면 1.

- 11-11 백업 복사본(밤 색인을 지금 원본으로 채움, 문서 1,691 · 수집 1,701 · 우리 글 251조각, 벡터 없음 0)으로 전·per_doc 1·per_doc 2를 쟀다. 표는 devlog.
- 출처 질문 5개: 정답 순위(전체)가 질문 1번 4 → 2(per_doc 1) · 3(per_doc 2), 나머지는 그대로다. 떨어진 질문은 없다.
  - 질문 2번 "수집 자료만" 검색에서 정답 기사가 상위 5개 밖(-)에서 4등으로 들어왔다(per_doc 1).
  - 중복 문서(같은 묶음이 두 자리 이상)는 전 4개 질문 → per_doc 1에서 0이다. per_doc 2에서는 4개 질문에 그대로 남는다(질문 1·3번은 자리 수만 줄고, 2·4번은 같음).
- 문서 질문 20개(`run_eval`): 세 경우 모두 표가 같다(0.65에서 답함 15/15 · 상위 1개 13/15 · 상위 3개 15/15 · 근거 없음 5/5). 질문별 정답 순위도 같다.
  - 같은 파일이 이미 나온 뒤 또 차지한 자리: 75자리 중 34 → 0(per_doc 1) · 21(per_doc 2).
- 그래서 **1**. 정답이 더 위로 오는 쪽도 1이었다(질문 1번 2등 대 3등).

### 우리 글 근거의 글 주소

- 색인 본문(`sources_db.py`의 문서 모양)은 그대로 둔다.
- `nsm/rag/answer.py`가 `doc_qa.sources`를 만들 때 `kind == "posts"`인 근거에 `links`(플랫폼 → 주소)를 넣는다.
  - 조회는 `Repository.publication_links(content_ids)`(게시됨이고 주소가 있는 것만)로 질문 한 번에 한 번이다.
  - `doc_qa.sources`는 JSON이라 키만 늘었다. 예전 기록은 `links` 없음 → 빈 dict로 읽는다(R4의 `kind`와 같은 방식).
- 화면(`ask.html`)은 근거를 펼친 안쪽 첫 줄에 "스레드 글 보기 · 인스타그램 글 보기"를 보여 준다.
  - `ask_format.post_links`가 http·https 주소만 링크로 만든다. 이스케이프는 템플릿 자동 이스케이프다.
  - 새 탭으로 열고 `rel="noopener noreferrer"`를 붙인다.
- 기록에 주소를 함께 저장한 것은 근거 본문을 저장한 이유(R3c)와 같다. 나중에 기록을 열어도 그때 본 근거를 그대로 보인다.

## 결과

- 쉬워진 것
  - 상위 5자리가 서로 다른 문서 다섯이 된다. 같은 원고의 두 벌, 같은 기사·같은 파일의 여러 조각이 다른 근거를 밀어내지 않는다.
  - 우리 글 근거에서 실제 글로 바로 간다. 다음 배치(성과 지표를 같은 자리에 붙이기)는 `_attach_post_links`·`publication_links`와 같은 길로 붙이면 된다.
  - ADR 0065 "다시 볼 조건"의 "출처마다 상위 n개"는 이 ADR로 대신한다. 측정에서 한 출처가 다른 출처를 밀어낸 것은 대부분 같은 문서의 여러 조각이었다.
- 어려워진 것·감수하는 것
  - **긴 문서의 다른 절이 근거에서 빠진다.** 답이 한 ADR의 두 절에 걸쳐 있으면 1등 절만 Claude에게 간다. `run_eval`은 파일 단위로만 정답을 봐서 이것을 잡지 못한다.
  - 같은 원고의 카드 문서가 1등이면 그 원고의 본문 조각(캡션·스레드 글)은 빠진다(질문 3번). 카드에 원고 요지가 있어 답은 되지만 본문의 세부는 안 간다.
  - SQL이 후보를 최대 80개(k 20일 때) 가져온다. 조각 3,600여 개 전수 비교라 차이는 없다.
- 다시 볼 조건
  - 답이 "문서에 그 내용이 없습니다"로 끝났는데 같은 문서의 다른 절에 답이 있던 사례가 보이면 `rag.per_doc`을 2로 올린다(설정 화면에는 없고 `~/.nsm/config.yaml`의 `rag:` 아래).
  - 측정 질문에 "같은 문서의 두 절이 다 필요한" 질문을 더해 절 단위 정답을 잴 수 있게 되면 기본값을 다시 잰다.
