# 0041. 안정화: 계속 0건 알림, 매일 데이터 백업, 실행 기록 보관 기간

- 상태: 제안 (배치 C12. 선웅제: "1~4번 다 진행")
- 날짜: 2026-10-16
- 결정한 사람: 선웅제(범위), 배치 C12 기본값(기준 값)
- 관련: [ADR 0038](0038-instagram-rate-limit-rest.md), [ADR 0040](0040-run-log-shows-changes.md), [known-gaps.md](../known-gaps.md) 2절

## 배경

이번 주에 두 번, 실패 없이 조용히 멈췄다.

- 2026-10-13: 네이버 뉴스 구조 변경으로 관련 자료 0개
- 2026-10-14: 인스타그램 429. 하루 넘게 "로그인 필요"로 잘못 보였다.

둘 다 실패로 기록되지 않아 알림이 없었다. 원고·댓글·성과·설정은 모두 `data.duckdb` 파일 하나에 있는데 백업이 없다. 실행 기록(`run_logs`)은 하루 약 400줄씩 쌓이기만 한다.

## 선택지

- 0건 확인을 어디서 할까
  1. 새 잡
  2. **health 잡(30분마다) 끝에서 (채택)**: 이미 자주 돌고, 로그인 점검과 같은 "멈춤 알아보기" 역할이다.
- 백업 방법
  1. 파일 복사: `nsm run`이 파일을 잡고 있어 Windows에서 읽을 수 없다(실제로 막혔다).
  2. `EXPORT DATABASE`: CSV/Parquet 폴더라 되살리기가 번거롭다.
  3. **`ATTACH` + `COPY FROM DATABASE` (채택)**: 같은 프로세스 안에서 DuckDB 파일 하나로 통째로 복사한다. 되살릴 때는 파일을 바꿔 넣기만 하면 된다. 10만 줄 기준 0.04초, 키·제약도 복사됐다.
- 백업 시점
  1. 게시·수집 직후
  2. **매일 새벽 04:30 새 잡 `maintenance` (채택)**: 지표 읽기(03:10) 뒤 다른 작업이 드문 때다. 대시보드 "지금 실행"의 "백업·정리"로 바로 할 수도 있다.

## 결정

- **계속 0건**(`nsm/engine/watchdog.py`, 기준 `stall_alert_days` 기본 2일)
  - 자료 모으기: 그 기간에 자료 모으기가 2번 이상 성공했는데, 관련도 기준 이상인 자료가 0개다.
    - 건너뛴 실행과 실패한 실행은 세지 않는다. 실패는 "잡 실패" 알림이 따로 가고, PC가 꺼져 있던 경우도 걸리지 않는다.
  - 게시: 그 플랫폼에 기간보다 오래 기다린 원고(대기·재시도 대기)가 있는데, 그동안 한 건도 못 올렸다.
    - 이유가 이미 보이는 경우는 뺀다. 로그인으로 멈춤(따로 알림), 요청 제한으로 쉬는 중(따로 알림), 하루 한도 0(일부러 안 올림)이다.
    - 페르소나를 꺼 두면 확인하지 않는다.
  - 찾으면 "오늘 할 일"에 띄운다.
  - 같은 종류(자료 모으기, 플랫폼별 게시)는 하루 한 번만 "계속 0건" 알림을 보낸다. 문장 속 숫자(대기 원고 수)가 바뀌어도 다시 알리지 않는다.
  - 풀리면 기록을 지운다. 같은 날 다시 걸리면 다시 알린다.
  - 확인 중 오류가 나도 health 잡의 로그인 점검 결과는 그대로 남긴다.
- **백업**(`Database.backup_to`, `maintenance` 잡)
  - 파일: `<NSM_HOME>/backups/data-YYYY-MM-DD.duckdb`
  - 임시 파일에 다 쓴 뒤 이름을 바꿔, 반쯤 쓴 백업이 남지 않게 한다.
  - 같은 날 다시 돌면 덮어쓴다. 최근 `backup_keep`(7)개만 남긴다. 방금 만든 백업은 날짜가 뒤로 가도(시간대 변경) 지우지 않는다.
  - 실패하면 임시 파일을 지우고 잡 실패로 기록한 뒤 알림을 보낸다.
  - 실행 기록 정리를 백업보다 먼저 해서, 백업이 실패해도 정리는 된다.
- **실행 기록 정리:** `run_log_keep_days`(90)일 넘은 `run_logs`만 지운다. 원고·댓글·성과·비용은 건드리지 않는다.
- **스케줄러 종료:** 일시정지하고 하던 한 바퀴를 기다린 뒤 멈춘다. APScheduler 3은 상태를 먼저 '멈춤'으로 바꾼 뒤 잠금을 잡는데, 그 사이 작업 제거가 끼면 `JobLookupError`가 났다.

## 결과

- 화면 구조 변경이나 요청 제한으로 조용히 멈춰도 2일 안에 알 수 있다.
- 실수나 파일 손상이 생겨도 하루 전 상태로 되살릴 수 있다. 방법은 사용설명서 7절에 있다.
- 어려워진 것
  - 백업은 같은 PC 안에만 있다. 디스크 고장에는 대비되지 않는다(known-gaps 4절).
  - 하루 안의 0건은 알림이 없다.
- 다시 볼 조건
  - 알림이 너무 잦거나 늦으면 `stall_alert_days`를 바꾼다.
  - 데이터가 커져 백업이 오래 걸리면 주기나 보관 수를 줄인다.
