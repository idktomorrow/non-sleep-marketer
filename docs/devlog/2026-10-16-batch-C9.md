# 2026-10-16 배치 C9: 인스타그램 요청 제한(HTTP 429) 감지와 댓글 확인 간격

## 목표

대시보드 실행 기록에 인스타그램 댓글 확인이 5분마다 "instagram 로그인 필요: 로그인돼 있지 않음"으로 실패했다. 사용자가 이유를 물었고, 원인을 찾은 뒤 "429 감지와 댓글 확인 간격 수정"을 배치로 하기로 했다.

## 한 일

- **원인 확인.**
  - 로그에서 첫 실패는 2026-10-14 20:24 인스타그램 게시의 `net::ERR_HTTP_RESPONSE_CODE_FAILURE`였다. 그 뒤로 댓글 확인이 하루 넘게 계속 실패했다.
  - 같은 시간 로그인 점검(health)은 성공이었고, 10-15 게시도 두 번 성공했다. 로그인은 살아 있었다.
  - Aside로 글 페이지 8개를 읽기 전용으로 열었다. 모두 Chrome 오류 화면 "HTTP ERROR 429"였다. 홈은 정상이었다.
  - 오류 화면에는 내 프로필 사진이 없어서 핸들 확인이 "로그인 안 됨"으로 보고했다.
- **감지 (`nsm/adapters/platforms/aside_common.py`)**
  - JS `nsmCheckPage`: 핸들을 읽기 전에 오류 화면인지 본다. 429 문구면 `ratelimit`, 그 밖의 Chrome 오류 화면은 `page`(일반 오류)다.
  - 로그인 점검(health) 스크립트도 같은 검사를 거친다(인스타그램·스레드).
  - `RateLimitedError(retry_at)`: 2시간 쉬고, 다시 막히면 4·8시간(최대)으로 늘린다. 성공하면 처음으로 돌아간다.
  - 쉬는 동안은 브라우저를 열지 않고 바로 이 예외를 낸다.
- **잡 (`nsm/engine/rate_limit.py`, health·reply·publish·metrics)**
  - 포트가 동결이라 어댑터 예외 클래스를 가져오지 않는다. `retry_at`·`blocked_until` 속성으로 알아본다.
  - health는 멈추지 않고, "로그인 필요"를 보내지 않는다.
  - reply·metrics는 실패가 아니라 `rate_limited`(쉬는 중)로 적는다.
  - publish는 쉬는 동안 그 플랫폼을 건너뛴다. 재시도 횟수는 쓰지 않는다.
  - 알림 "인스타그램 요청 제한"은 쉬는 구간마다 한 번만 보낸다.
- **인스타그램 댓글 확인 간격**
  - `instagram_comment_interval_minutes`(기본 30분, 설정 화면 칸 추가)
  - `instagram_comment_lookback_days`(기본 3일)
  - 확인 시도 시각은 실패해도 기록한다. 대시보드 "지금 실행"은 간격을 무시하지만, 쉬는 중이면 쉰다.
- **문서:** ADR 0038(제안), 사용설명서(설정값 표, 5절 "요청 제한에 걸리면", 문제 해결 표), architecture(잡 표·구현 상태), known-gaps, CHANGELOG

## 막힌 것과 해결

- **"로그인 필요"가 거짓이었다.**
  - 처음에는 로그인이 풀렸다고 생각할 만했다. 그런데 30분마다 도는 로그인 점검과 게시는 성공이었다.
  - 두 경로의 차이는 여는 페이지(홈 대 글 페이지)뿐이었다. 그래서 글 페이지를 직접 열어 봤다.
- **진단 자체가 요청을 늘린다.** 막힌 상태에서 확인 요청을 더 보내면 제한이 길어질 수 있다. 진단은 글 8개를 한 번, 고친 코드 확인은 글 1개를 한 번만 열었다.
- **엔진이 어댑터 예외를 알 수 없음.**
  - `nsm/ports/`가 동결이라 새 예외를 포트에 더하지 않았다.
  - 대신 예외 객체의 `retry_at`, 어댑터의 `blocked_until` 속성으로 알아보게 했다. 드라이런·가짜 어댑터는 이 속성이 없으니 그대로 동작한다.
- **코드 리뷰(`/code-review`) 반영.**
  - 답글을 달다 막히면 남은 댓글이 "자동 처리 실패"로 사람에게 넘어갔다. 이제 `new`로 두고 쉬고 나서 처리한다.
  - 댓글 스크립트가 첫 글에서만 페이지를 검사해 둘째 글부터의 429를 못 알아봤다. 이제 글마다 검사한다(스레드도).
  - 뒤 묶음의 429를 경고로 삼키고 부분 결과를 돌려줬다. 그러면 마지막 댓글 시각이 앞당겨져 못 읽은 글의 댓글을 잃는다. 이제 요청 제한을 그대로 올린다.
  - `ERR_HTTP_RESPONSE_CODE_FAILURE`는 404·500에도 나온다. 요청 제한 판정에서 뺐다.
  - 게시가 429로 여러 번 막히면 재시도 횟수를 다 써 "게시 포기"가 됐다. 저장소에 `refund_attempt`를 더해 횟수를 쓰지 않게 했다.
  - 홈 화면 로그인 점검의 성공이 백오프를 초기화해 2시간만 반복됐다. 점검 성공은 초기화하지 않는다.
  - 지표가 중간에 막히면 넣은 수를 잃었다. 고쳤다.
  - 알림 조사 "스레드이"를 "스레드가"로 고쳤다.
  - 일시 오류에도 인스타그램 확인 간격(30분)을 지키는 것은 의도대로 둔다. 막힌 플랫폼을 자주 두드리지 않는 것이 목적이다.
- **잡 지터와 간격.** 댓글 확인 잡은 5분 ±1분으로 돈다. 30분 간격을 정확히 재면 35분마다가 되기 쉬워 2분 여유를 두었다.

## 배운 것 (신입 개발자용)

1. **오류 메시지는 "관찰"이지 "원인"이 아니다.** "로그인돼 있지 않음"은 "프로필 사진이 안 보였다"를 해석한 말이었다. 같은 계정으로 다른 경로(홈 화면 점검, 게시)가 성공하면 해석을 의심하고, 실패하는 그 화면을 직접 본다.
2. **429는 "잠깐 쉬어라"라는 뜻이다.** 서버가 요청이 너무 많다고 막을 때 계속 두드리면 제한이 길어진다.
   - 막히면 정해진 시간 요청을 끊고(서킷 브레이커), 또 막히면 쉬는 시간을 늘린다(지수 백오프).
   - 평소 요청량도 줄인다. 이번에는 30분 간격, 최근 3일 글만.
3. **동결된 인터페이스를 안 바꾸고 새 신호 전달하기.** 포트(`nsm/ports/`)에 예외를 더하면 두 사람 합의가 필요하다.
   - 대신 예외 객체에 속성(`retry_at`)을 달고, 받는 쪽은 `getattr`로 본다(덕 타이핑).
   - 이 속성을 모르는 구현(드라이런·가짜)에는 영향이 없다.

## 다음 배치 메모

- 머지 후 `nsm run`을 다시 켜면 인스타그램을 한 번 다시 시도한다. 아직 막혀 있으면 "인스타그램 요청 제한" 알림이 한 번 뜨고 2시간 쉰다.
- 30분 간격에서도 429가 반복되면 간격을 60분으로 늘리거나, 확인할 글 수를 더 줄인다(ADR 0038 "다시 볼 조건").
- 쉬는 상태는 메모리에만 있다. 대시보드 개요에 "쉬는 중" 표시가 필요하면 그때 DB에 둔다.
