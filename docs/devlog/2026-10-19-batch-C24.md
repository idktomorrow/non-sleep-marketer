# 2026-10-19 배치 C24: 실패 상황 5가지 검증

## 목표

포트폴리오 피드백에 "기능이 넓으니 예외 상황을 실제로 재현해 검증하라"는 질문 5개가 있었다. 사용자가 "검증 기록"을 원했다.

1. SNS 게시는 됐는데 응답만 실패하면 중복 게시되지 않나
2. 승인과 수정이 동시에 오면 어떤 판이 게시되나
3. 답글을 보낸 직후 프로그램이 죽으면
4. AI 생성이 오래 걸리면 다른 작업은
5. AI 비용이 상한을 넘지 않나

이미 테스트가 있는 것은 근거만 적고, 빈틈은 고치고 테스트를 더한다.

## 한 일

| 질문 | 확인 결과 | 한 일 |
|---|---|---|
| 1 중복 게시 | 올리기 전 내 최근 글을 읽어 멱등 처리, 게시 중 중단은 검토 대기열로. 테스트 있음 | 근거 기록만 |
| 2 승인·수정 동시 | 화면은 검토 대기만 수정 허용. 그러나 저장(`update_generated`)은 조건 없는 UPDATE라, 검사와 저장 사이에 승인이 끼면 승인된 원고가 검사 없이 바뀔 수 있었다 | `WHERE status='pending_review'` 조건부 UPDATE로, 0건이면 `InvalidTransitionError` → 화면 409. 테스트 추가 |
| 3 답글 중 중단 | 댓글은 처리가 끝날 때까지 'new'였다. 보낸 직후 죽으면 다음 실행이 'new'로 보고 **다시 보내 두 번 달릴 수 있었다** | 보내기 전에 'replying'으로 적고, 켤 때 남은 'replying'은 재전송 없이 "확인 필요"로(`recover_interrupted_replies`, 게시의 `recover_interrupted`와 같은 자리). 테스트 추가 |
| 4 긴 AI 호출 | 작업 스레드 하나라 순서대로 기다린다(설계). 그런데 Claude 클라이언트에 시간 제한이 없어 SDK 기본 10분×재시도 5번, 최악 1시간 가까이 모든 작업이 멈출 수 있었다 | 원고 180초·분류 60초(재시도 5번은 순간 끊김용으로 그대로). 테스트 추가 |
| 5 비용 상한 | 원고·키워드 원고는 만들기 전 상한 확인. 마지막 1건은 조금 넘길 수 있음(3~6센트). 답글·이미지 읽기는 상한 밖(각 0.3·0.02센트, 작성자당 하루 3건) | 근거와 한계를 known-gaps에 기록. 6일 실측 $0.61 |

결과 표는 `docs/known-gaps.md` 2-1절에 두었다.

## 막힌 것과 해결

- **'replying'을 언제 복구하나.** 매 실행마다 복구하면 대시보드의 "직접 답글"(요청 스레드에서 'replying'으로 바꾼 뒤 작업 스레드로 보냄)과 경쟁해 보내기도 전에 "중단됨"으로 바꿀 수 있다. 그래서 게시 복구와 같은 **켤 때 한 번**으로 두었다. 작업 스레드가 하나라 켜진 뒤에는 '보내는 중'이 남아 있을 수 없다.
- **승인된 원고를 테스트가 고치고 있었다.** C18 테스트가 픽스처(이미 승인됨)의 출처 정보를 `update_generated`로 넣고 있었다. 사람 편집 경로가 아니라 DB 직접 갱신으로 바꿨다.
- **시간 제한 값.** 원고 1건은 실측 30~60초(카드 덱 + 캡션 + 스레드 글)라 180초, 분류는 수 초라 60초로 잡았다. 이미지 읽기는 C16에서 이미 60초였다.

## 테스트 결과

- `uv run ruff check .`, `uv run ruff format --check .` 통과
- `uv run pytest`: PR 본문 참고
  - `test_reply_marks_replying_before_sending_and_recovers_after_crash`: 보내기 전 'replying', 중단 뒤 복구는 재전송 없이 escalated + 알림, 이후 실행이 건드리지 않음
  - `test_edit_after_approval_is_refused_at_the_database`: 승인 뒤 DB 저장 거부 + 화면 409
  - `test_claude_clients_have_timeouts`: 생성·분류 클라이언트 모두 timeout ≤ 180

## 배운 것 (신입 개발자용)

1. **"있다"와 "검증했다"는 다르다.** 질문 5개 중 2개는 테스트가 이미 있었고, 2개는 코드만 읽어서는 "괜찮아 보였는데" 실제로는 빈틈이었다(재전송, 무제한 대기). 질문을 테스트로 바꿔 보면 빈틈이 드러난다.
2. **멱등하지 않은 동작 앞에는 상태를 먼저 적는다.** "보내는 중"을 먼저 적고 보내면, 중간에 죽어도 다음 실행이 "모르는 상태"를 알아보고 사람에게 넘길 수 있다. 게시(`publishing`)와 답글(`replying`)이 같은 패턴이다.
3. **외부 호출에는 항상 시간 제한.** 라이브러리 기본값은 내 상황을 모른다. 스레드가 하나인 프로그램에서 10분 대기 × 재시도 5번은 전체 정지와 같다. 값은 실측(원고 30~60초)에서 정한다.
