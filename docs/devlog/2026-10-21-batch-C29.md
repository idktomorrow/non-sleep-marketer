# 2026-10-21 배치 C29: 프리셋 (페르소나·브랜드·작업 공간 갈아끼우기)

## 목표

설정 화면에서 페르소나를 이름 붙여 저장하고 전환한다. 사용자 결정: 자료·댓글·성과도 프리셋별로. "결과물을 보고 롤백할지 결정" → 되돌리기 쉬운 구조로.

## 한 일

- `nsm/config/presets.py` `PresetStore`: `presets/<이름>/preset.yaml`(페르소나·브랜드, 계정 핸들 제외) + `brand/`(캐릭터 그림 복사) + `data.duckdb`. 기본 프리셋은 기존 DB 그대로. 이름 규칙(30자, 경로 문자 금지), 지우기 보호(지금 것·기본).
- `Database.switch(path)`: lock 안에서 연결만 갈아끼움. 커서 생성도 lock 안으로 옮김(전환 도중 옛 연결을 잡지 않게).
- `runtime.switch_preset(ctx, db, name, save)`: 지금 프리셋 자동 저장 → 대상 설정 입히기 → DB 교체 → 설정 저장·반영(활동 시간 바뀌면 재예약) → 새 DB 복구 → 알림. 작업 스레드에서(`scheduler.submit`) 돌고 오른쪽 아래 진행 표시에 "프리셋 전환"으로 보인다.
- 설정 화면 맨 위 "프리셋" 칸(목록·전환·지우기·지금 설정을 저장), 상단 바에 프리셋 이름 배지. `settings.preset` 설정값.
- ADR 0049, 설명서 4절 "프리셋", 저장 위치 표, known-gaps, CHANGELOG. 버전 0.4.4.

## 막힌 것과 해결

- **어디까지 프리셋에 넣나.** 계정 핸들은 실계정과 묶여 있어 프리셋이 바꾸면 "로그인 계정이 다르다"로 게시가 막힌다 → 핸들은 프리셋 파일에서 빼고 전환 때 지금 것을 지킨다. 운영 설정(간격·상한·알림)도 공통.
- **DB 교체 타이밍.** 대시보드 요청 스레드와 작업 스레드가 같은 `Database`를 쓴다. `execute`가 커서를 lock 밖에서 만들고 있어서 교체 순간 옛 연결의 커서를 잡을 수 있었다 → 커서 생성을 lock 안으로. 교체 자체는 작업 스레드에서만(잡과 직렬).
- **비용 상한.** 비용 기록이 DB 안이라 프리셋마다 따로 센다. 공통 장부를 만들면 Repository가 DB 두 개를 알아야 해서 이번엔 한계로 적고 넘어갔다(ADR 0049).
- **되돌리기.** 기본 프리셋 DB를 옮기지 않은 덕에 롤백은 `preset: 기본` + `presets/` 삭제로 끝난다.

- **코드 리뷰 지적 10건(모두 반영)**: ① 켤 때 항상 기본 DB를 열어 재시작하면 프리셋 설정 + 기본 DB가 섞이던 치명적 버그 → `workspace_db_path(cfg)`로 설정이 가리키는 DB를 연다. ② "내 브랜드"/"내-브랜드"처럼 같은 폴더가 되는 이름이 지우기 보호를 피해 가던 것 → 비교를 slug 기준으로, 다른 이름의 기존 폴더 위 저장은 거부. ③ 백업이 프리셋 구분 없이 `data-날짜`로 덮어쓰던 것 → `data-<프리셋>-날짜`, 보관 개수도 프리셋별. ④ `Database.switch`가 새 파일을 열다 실패해도 옛 연결을 닫던 것 → 새 파일을 먼저 열어 스키마까지 확인한 뒤 교체. ⑤ `fetchall`과 `queries._rows`의 커서가 lock 밖 → `Database.query()`로 커서 생성~fetch를 lock 안에서. ⑥ DB 교체 뒤 설정 저장이 실패하면 둘이 어긋남 → 설정 먼저 저장, DB 교체 실패 시 설정 되돌림. ⑦ 빈 이름으로 전환하면 500 → 안내. ⑧ 다른 기존 프리셋을 조용히 덮어쓰고 "만들었습니다"라 하던 것 → 거부. ⑨ 런타임이 자체 `PresetStore()`를 만들어 대시보드와 다른 폴더를 볼 수 있던 것 → 하나를 만들어 둘 다에 주입. ⑩ 템플릿에 '기본'이 하드코딩 → `default_preset` 전역.

## 배운 것 (신입 개발자용)

1. **"설정 바꾸기"와 "작업 공간 바꾸기"는 다른 기능이다.** 판정 결과가 DB에 닫혀 있으면 설정만 바꿔도 과거 판정이 새 설정을 오염시킨다. 무엇이 설정에 종속된 데이터인지 먼저 적어 보면 답이 나온다.
2. **격리는 필터보다 파일이 싸다.** 조회 40개에 `WHERE preset=?`를 다는 것보다 파일을 나누는 게 코드가 적고 새는 곳이 없다. 대신 "둘을 합쳐 보는" 기능은 비싸진다 — 어느 쪽이 더 자주 필요한지로 고른다.
3. **갈아끼우기는 "새것을 다 준비한 뒤 바꾸고, 옛것을 마지막에 닫는다."** 새 DB를 열다 실패했는데 옛 연결을 먼저 닫으면 돌아갈 곳이 없다. 설정과 DB처럼 둘이 짝인 상태는 한쪽이 실패하면 다른 쪽을 되돌리는 코드가 꼭 있어야 한다(리뷰에서 배움). 공유 객체를 갈아끼울 땐 "만드는 순간"도 잠가야 한다: 연결을 lock 안에서 바꿔도, 커서를 lock 밖에서 만들면 교체 직전의 옛 연결을 잡는다. 잠금은 사용뿐 아니라 획득 지점까지 덮어야 한다.
