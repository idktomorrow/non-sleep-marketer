# 2026-10-20 배치 C26: 버전 표시, 다음 게시 시각

## 목표

사용자가 고른 운영 편의 두 가지.
- 화면에 버전 번호만 깔끔하게. "몇 시에 켬", "재시작 필요" 같은 문구는 없이.
- "오늘"의 게시 대기 칸에 다음 게시 예정 시각.

## 한 일

- **버전 번호**(`nsm.app_version()`, 바닥글 "논슬립 마케터 v0.4.1")
  - 설치 정보(`importlib.metadata`)에서 읽는다. `nsm run`은 켤 때 동기화하므로 이 값은 "지금 켜진 코드"의 버전이다. 코드를 머지해도 다시 켜기 전까지는 예전 번호가 보인다. 그래서 별도 안내 없이 번호만으로 재시작 여부를 안다.
  - 규칙: PR마다 `pyproject.toml` 끝자리 +1(CLAUDE.md DoD 10). 안정화 태그 때 가운데 자리. 시작은 0.4.1.
- **다음 게시 시각**(`nsm/app/next_publish.py`)
  - 게시 잡이 보는 조건을 같은 순서로 따라가 플랫폼별 "가장 이른 시각"을 센다: 대기 중이면 지금/실패 재시도면 그 시각 → 요청 제한으로 쉬는 중이면 그 뒤 → 같은 플랫폼 간격 → 오늘 한도를 다 썼으면 내일 → 게시 시간 안으로(`policy.next_window_start`, 자정을 넘는 구간도 처리).
  - 승인된 원고가 없으면 기존 문구 그대로. 있으면 "다음 게시 인스타그램 08:05 · 스레드 11:30"처럼. 다른 날이면 "10/21 08:00".
  - 정확한 예약이 아니라 "이 시각 이후 첫 게시 차례"다(게시 잡은 30분마다 돈다). 설명서에 그렇게 적었다.

## 막힌 것과 해결

- **"버전 = 지금 켜진 코드"를 어떻게 보장하나.** `pyproject.toml`을 직접 읽으면 머지만 해도 번호가 바뀌어 재시작 여부를 알 수 없다. 설치 정보에서 읽으면 켤 때 값이 고정된다. 테스트·개발처럼 설치 전이면 pyproject로 대신한다.
- **게시 잡 코드를 복사하지 않기.** 다음 시각 계산은 `run_publish`의 분기와 같아야 한다. 잡 코드를 그대로 쓰기엔 ctx가 필요해서, 같은 저장소 함수(`last_published_at`, `count_published_between`, `publications_in_status`)와 같은 정책 함수를 쓰는 작은 모듈로 두고, 분기 순서를 주석으로 맞췄다. 잡 쪽이 바뀌면 여기도 같이 봐야 한다(architecture 표에 적음).

## 배운 것 (신입 개발자용)

1. **"무엇의 버전인가"를 먼저 정한다.** 저장소의 버전과 실행 중인 프로그램의 버전은 다를 수 있다. 사용자가 알고 싶은 건 후자다. 어디서 읽느냐(설치 정보 vs 파일)가 답을 가른다.
2. **같은 규칙은 한 곳에서.** 게시 잡과 화면이 "언제 올릴 수 있나"를 각자 계산하면 어긋난다. 정책 함수와 저장소 함수를 공유하고, 순서를 맞춘 뒤 테스트로 고정한다.
3. **화면 문구는 거짓말하지 않게.** "다음 게시 08:05"는 예약이 아니라 "그 뒤 첫 차례"다. 그대로 적어야 사용자가 08:05에 안 올라갔다고 오해하지 않는다.
