# 2026-10-16 배치 C12: 안정화 (계속 0건 알림, 데이터 백업, 실행 기록 정리, 스케줄러 경고)

## 목표

프로토타입 기능은 거의 다 들어갔다. 다음 단계로 "켜 두면 혼자 안정적으로 돌고, 문제가 생기면 바로 알 수 있게"를 제안했고, 사용자가 안정화 1~4번을 모두 진행하기로 했다.

1. 계속 0건 알림
2. 데이터 자동 백업
3. 오래된 실행 기록 정리
4. 가끔 나는 테스트 경고 고치기

5번(1주일 켜 두고 관찰)은 머지 후에 한다.

## 한 일

- **계속 0건 알림** (`nsm/engine/watchdog.py`)
  - health 잡(30분마다)이 확인한다.
  - 자료 모으기: 2일 동안 2번 이상 돌았는데 관련 자료가 0개면 걸린다.
  - 게시: 2일보다 오래 기다린 승인 원고가 있는데 그동안 0건이면 걸린다.
  - 찾으면 오늘 할 일에 "계속 0건"으로 띄우고, 같은 문장은 하루 한 번만 알린다.
  - 저장소에 `runs_since`, `relevant_since`, `waiting_publications`를 더했다.
- **데이터 자동 백업** (`Database.backup_to`, 새 잡 `maintenance` 매일 04:30)
  - 파일 복사 대신 `ATTACH` + `COPY FROM DATABASE`로 DuckDB 파일 하나를 통째로 만든다.
  - 임시 파일에 다 쓴 뒤 이름을 바꾼다. 최근 7개만 남긴다.
  - 대시보드 "지금 실행"에 "백업·정리"가 생겼다.
- **실행 기록 정리:** 같은 잡에서 90일 넘은 `run_logs`를 지운다(`prune_runs`).
- **스케줄러 경고:** 종료할 때 일시정지하고, 하던 한 바퀴를 기다린 뒤 멈춘다.
- **화면·문장**
  - 실행 기록 상태 표와 요약 문장에 "백업·정리"를 더했다.
  - 로그인 점검 요약에 계속 0건 문장을 붙였다.
- **설정(config.yaml):** `stall_alert_days`(2), `backup_keep`(7), `run_log_keep_days`(90)
- **문서**
  - ADR 0041(제안)
  - 사용설명서: 저장 위치, 설정값, 문제 해결의 "계속 0건"과 되살리는 법
  - known-gaps(해결한 두 줄 정리, "백업은 같은 PC 안에만" 추가), architecture, CHANGELOG

## 막힌 것과 해결

- **백업할 파일을 읽을 수 없음.** `nsm run`이 `data.duckdb`를 잡고 있어 Windows에서 복사가 막혔다(`cp`도 "busy"). 같은 프로세스의 DuckDB 연결에서 새 파일을 `ATTACH`하고 `COPY FROM DATABASE`로 옮겼다.
  - 10만 줄 기준 0.04초였다. 기본 키 등 제약도 복사됐다.
- **스케줄러 경고의 원인.** APScheduler 3의 `shutdown()`은 상태를 '멈춤'으로 먼저 바꾸고 잠금을 잡는다. 그 사이 스케줄러 스레드가 방금 끝난 일회성 작업을 지우려 하면, '멈춤' 상태라 대기 목록에서 찾다가 `JobLookupError`가 난다.
  - 일시정지로 새 바퀴를 막고, 잠금을 한 번 잡아 하던 바퀴를 기다린 뒤 멈추게 했다.
  - 고치기 전에는 6번 중 3번 경고가 났고, 고친 뒤 15번 모두 깨끗했다.
- **내 실수 하나.** 실행 기록 쿼리의 시각 인자를 `to_db()`로 감싸야 한다고 잘못 판단했다. 저장소의 `_now()`가 이미 DB 형식(UTC, 시간대 없음)을 돌려줘서 테스트가 바로 실패했고, 되돌렸다.
- **코드 리뷰(`/code-review`) 반영(10건).**
  - 알림 중복 막기를 문장 대신 종류(자료 모으기, 플랫폼별 게시)로 바꿨다. 대기 원고 수가 바뀌면 같은 날 또 알리던 문제다.
  - 풀린 종류는 기록에서 지워, 같은 날 다시 걸리면 다시 알린다.
  - 이유가 이미 보이는 플랫폼은 게시 0건에서 뺐다. 하루 한도 0, 요청 제한으로 쉬는 중이다.
  - 실패한 자료 모으기는 세지 않는다. "잡 실패" 알림과 겹치고 원인을 잘못 짚었다.
  - 계속 0건 확인에서 오류가 나도 health 잡의 로그인 점검 결과가 남게 했다.
  - 백업
    - 실행 기록 정리를 백업보다 먼저 한다.
    - 실패하면 임시 파일을 지운다.
    - 방금 만든 백업은 날짜가 뒤로 가도 지우지 않는다.
  - 스케줄러
    - 내부 잠금(`_jobstores_lock`)이 없는 버전이면 기다리지 않고 멈춘다.
    - 리뷰는 일회성 작업을 별도 스레드 풀로 옮기라고 권했다. 하지만 "모든 작업이 한 스레드에서 차례로"라는 설계(브라우저·DB 동시 접근 방지)를 깨므로 하지 않았다.
  - `prune_runs`를 DELETE 한 번으로 했다.
  - "최근 7개" 고정 문구를 설정값 기준으로 바꿨다.
- **0건이 문제인지 아닌지.** PC가 꺼져 있었으면 자료가 0개인 게 당연하다. 그래서 "그 기간에 자료 모으기가 2번 이상 실제로 돌았는데(건너뜀 제외)"를 조건으로 넣었다.
  - 게시도 원고가 없으면 0건이 당연하다. 그래서 "기간보다 오래 기다린 원고가 있을 때만" 본다.

## 배운 것 (신입 개발자용)

1. **"실패"와 "아무 일도 안 일어남"은 다르다.** 오류 처리는 실패만 잡는다. 화면 구조가 바뀌어 "0건 성공"이 이어지는 것은 결과를 보고 따로 알아봐야 한다(워치독). 이때 "0이 당연한 경우"(PC 꺼짐, 원고 없음)를 빼야 거짓 알림이 안 난다.
2. **백업은 되살려 봐야 백업이다.** 파일이 생긴 것만으로는 부족하다. 실제로 그 파일을 열어 데이터가 있는지, 바꿔 넣으면 앱이 여는지까지 확인했다. 쓰는 도중 꺼져도 망가진 백업이 남지 않게 "임시 파일에 쓰고 이름 바꾸기"를 했다.
3. **가끔 나는 경고는 경합(race)일 때가 많다.** 매번이 아니라 가끔이면 두 스레드의 순서 문제를 의심한다. 라이브러리 코드를 직접 읽어 "상태를 바꾸는 시점"과 "잠금을 잡는 시점"이 어긋난 곳을 찾았고, 여러 번 돌려 사라진 것을 확인했다.
