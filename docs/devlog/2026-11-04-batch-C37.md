# 2026-11-04 배치 C37: 스레드 글이 안 열리면 "정상"이 아니라 오류로

## 목표

11-04 06:42부터 스레드 글 페이지가 본문 없이 열렸다("문제가 발생했습니다" + "다시 시도"). 그런데 댓글 확인은 13시간 동안 "새 댓글 없음"(성공)으로 지나갔다(incidents/0011). 할 일은 네 가지다.
- 플랫폼 오류 화면과 "기다렸는데 비었음"을 오류로 드러낸다.
- 계속 안 열리면 쉰다.
- 평소에 여는 페이지 수를 줄인다.
- 확인이 오래 걸리면 기록한다.

## 한 일

- **오류 화면 감지**(`aside_common.py` `nsmCheckPage`): 안내문("문제가 발생했습니다|Something went wrong|나중에 다시 시도|Try again later")과 "다시 시도" 버튼이 **함께** 있으면 `NsmError('page', '플랫폼이 오류 화면을 띄움')`로 던진다. 종류는 일시적이다.
- **`nsmEnsure(pg, 값, 문구, 종류)`**: 반드시 있어야 하는 요소를 기다린 결과가 비면 오류 화면을 한 번 더 보고, 아니면 던진다. 기본 종류는 `page`(일시적)다.
- **`nsmAssertHandle`와 health**: 로그인이 안 보이면 로그인 오류를 내기 전에 오류 화면을 한 번 더 본다. 그래서 E5의 빈 화면 판정보다 먼저 걸린다(요청 8).
- **reply 잡**(`nsm/engine/reply.py`)
  - 같은 플랫폼 댓글 조회가 일시적 오류로 연속 2번 실패하면 그 플랫폼 댓글 확인만 30분 쉬고, 연속 구간에 한 번 알린다.
  - 횟수는 `comment_fetch_failures` 키 하나에 두고, 성공하면 지운다. 게시는 그대로다.
  - 잡이 간격의 2배를 넘게 걸리면 "댓글 확인이 N분 걸림(간격 M분)"을 실행 기록과 장애 화면 실패 목록에 남긴다(알림 없음).
- **설정**
  - `threads_comment_interval_minutes`(새로, 기본 15, 5~180).
  - `comment_lookback_days`는 기본 14 → 7, 범위 1~30.
  - 둘 다 설정 화면 고급 칸에 있고, 작업 상태 표 문구에도 스레드 간격을 넣었다.
- **문서**: 장애 기록 0011, ADR 0062(0061은 C36이 먼저 씀), 설명서, architecture, CHANGELOG. 버전 0.4.22.

## 막힌 것과 해결

- **오류 문구만 보면 댓글에 속는다.** "문제가 발생했습니다"는 사람 댓글에도 나올 수 있다. 그래서 "다시 시도" 버튼이 함께 있을 때만 오류 화면으로 본다. 댓글로는 버튼을 만들 수 없다.
- **JS를 어떻게 테스트하나.** 지금까지 스크립트는 문자열 검사만 했다. 이번에는 node에서 실제 스크립트를 가짜 탭(`pg`)·가짜 `document`에 대고 돌리고, 진짜 실행기처럼 결과 줄을 읽는 `NodeRepl`을 만들었다. `sleep`이 가짜 시계를 돌려 20초 기다림이 바로 끝난다. 모든 스크립트의 `node --check` 문법 검사도 테스트로 넣었다.
- **기존 테스트 둘이 바뀌었다.**
  - 스레드가 잡마다(5분) 확인한다는 테스트를 15분 간격으로 고쳤다.
  - 간단 화면에서 숨는 고급 줄이 2개에서 3개가 됐다.
- **"장애 화면의 자동 진단에 보이게"**: Claude 진단은 화면 변경(`ui_changed`)이고 증거 폴더가 있을 때만 한다(E2). 느린 확인은 증거가 없어서, 장애 화면 실패 목록에 단계 `duration`·조치 "기록만(알림 없음)"으로 남겼다.

- **코드 리뷰 10건 중 9건 반영.**
  - ① 글 하나가 안 열려도 조회 전체를 버렸다. 그래서 지운 글 하나가 최대 7일 동안 모든 댓글을 막을 수 있었다 → 그 글만 건너뛰고, 모두 안 열릴 때만 실패.
    - 파이썬 쪽도 "읽은 묶음이 하나도 없을 때"만 던진다. 전에는 "댓글 0개"와 "못 읽음"을 구분하지 못했다.
  - ② 쉬기 알림이 Aside 꺼짐 같은 다른 일시적 실패에도 "게시물이 열리지 않아"라고 했다 → 오류 코드 `page`(어댑터가 `PlatformError.code`로 남김)만 센다.
  - ③ 다른 종류 실패가 끼어도 "연속"으로 셌다 → 끊는다.
  - ④ 쉬기에 들어가도 장애 화면 조치가 "다음 댓글 확인에 다시"였다 → "댓글 확인 30분 쉬기(연속 실패)".
  - ⑤ 오류 화면 판정이 페이지 아무 데의 문구와 버튼을 엮었다 → 버튼에서 네 칸 위까지 같은 칸에 안내문이 있을 때만.
  - ⑥ `nsmEnsure(pg, await nsmUntil(...))`가 13번 복사돼 있었다 → `nsmNeed(pg, fn, ms, 문구, 종류)` 하나로. 새로 반드시 기다릴 곳은 이것을 쓴다.
  - ⑦ 위 칸 "댓글 확인 간격"의 힌트가 "스레드 기준"이라 새 칸과 모순됐다 → 작업 간격이라고 고쳤다.
  - ⑧ 느린 확인 기록에 플랫폼별 시간이 없었다 → 가장 오래 걸린 조회 하나와 그 시간을 문구에 넣었다.
  - ⑨ 작업 상태 표가 켜지 않은 플랫폼 간격도 보였다 → 켠 플랫폼만.
  - 남긴 하나: 설정 화면에서 저장한 사용자는 파일에 14가 적혀 있어 새 기본값 7이 적용되지 않는다(운영 설정 파일도 그렇다). 일부러 고른 값과 구분할 수 없어 자동으로 바꾸지 않고, 설명서·ADR·배치 보고에 "설정 화면에서 7로"를 적었다.

## 배운 것 (신입 개발자용)

1. **"못 찾음"을 값으로 돌려주는 함수는 부르는 쪽이 꼭 확인해야 한다.** `nsmUntil`은 시간이 지나면 null을 돌려줄 뿐이다. 부르는 쪽이 그냥 지나가면 "본문이 안 열림"이 "댓글 0개"로 바뀐다. 실패가 성공으로 바뀌는 가장 흔한 길이다. 그래서 꼭 있어야 하는 것은 `nsmEnsure`처럼 던지는 함수로 감싼다.
2. **"0개"는 두 가지 뜻일 수 있다.** "정말 없음"과 "보지 못함"이다. 둘을 가르려면 "봤다"는 증거(여기서는 본문 글)를 따로 확인해야 한다. 본문이 떴는데 댓글이 없으면 0개, 본문도 없으면 오류다.
3. **얼마나 자주, 얼마나 많이 여는지가 부하다.** 5분마다 14일치 글 36개는 하루 9천 번이 넘는다. 간격을 3배로 늘리고 글을 7일로 줄이면 10분의 1이 된다. 숫자로 적어 보기 전에는 이렇게 많은 줄 몰랐다.
