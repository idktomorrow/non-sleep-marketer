# 2026-10-19 배치 C23: 보냈지만 확인 못 한 답글은 사람에게

## 목표

대시보드 "최근 댓글"에 "자동 답글"로 표시된 댓글이 인스타그램에는 답글이 없었다(10-19 16:47, baron_ghibli). 로그에는 "답글은 보냈지만 확인하지 못함" 경고만 남았고 화면은 성공처럼 보였다. 사용자가 "댓글 달았다고 뜨는데 안 달렸다"고 물었다.

## 한 일

- **어댑터 신호**: 인스타그램 어댑터는 답글 ID를 늘 빈 값으로 돌려줬다(웹 화면에서 ID를 얻을 수 없음). 이제 화면에서 답글이 확인되면 `seen:<댓글ID>` 표지를, 확인 못 하면 빈 값을 돌려준다. 스레드는 원래 확인되면 코드, 아니면 빈 값이었다. 포트(`reply -> str`)는 그대로다.
- **엔진**(`reply.py`): 답글 ID가 비어 있으면 "자동 답글"이 아니라 **"확인 필요"(escalated)**로 적고, 이유에 "답글을 보냈지만 플랫폼에서 확인하지 못함. 실제로 달렸는지 보고, 없으면 직접 답글을 보내세요"를 넣는다. 보내려던 문장은 `reply_text`로 남겨 댓글 화면에서 그대로 다시 보낼 수 있다. 작성자별 하루 한도는 센다(보냈을 수 있으므로).
- **재시도하지 않는다**: 확인 실패는 "안 나감"이 아니라 "모름"이다. 다시 보내면 두 번 달릴 수 있어, 판단을 사람에게 넘긴다. 기존 댓글 화면(직접 답글·처리 완료)을 그대로 쓴다. 새 화면·새 상태값은 없다.
- **문서**: CHANGELOG, 사용설명서(댓글 처리, 화면 표), known-gaps, architecture.

## 막힌 것과 해결

- **상태값을 더할 수 없다.** `CommentStatus`는 동결된 도메인 모델이다. "보냈지만 확인 못 함"을 새 상태로 만들지 않고, 기존 `escalated` + 이유 문장으로 표현했다. 화면도 그대로 동작한다.
- **인스타그램은 "확인됨"도 빈 값이었다.** 엔진이 빈 값을 "확인 못 함"으로 쓰려면 확인된 경우에 무언가를 돌려줘야 했다. 진짜 ID는 없으니 `seen:` 표지를 쓴다. DB의 `reply_external_id`에 그대로 저장되지만 다른 곳에서 ID로 쓰지 않는다.
- **왜 올라가지 않았는지는 아직 모른다.** 이번 배치는 "모르는 상태를 성공으로 표시하지 않기"까지다. 재발하면 전송 직후 화면을 저장해 보는 진단을 더한다.

## 배운 것 (신입 개발자용)

1. **"성공"의 정의를 좁힌다.** 버튼을 누른 것과 결과가 생긴 것은 다르다. 화면에는 결과가 생긴 것만 성공으로 보여 주고, 모르는 것은 모른다고 보여 줘야 사람이 올바르게 개입한다.
2. **재시도는 멱등할 때만.** 답글 전송은 두 번 하면 두 개가 달린다. 확인 실패를 자동으로 재시도하지 않고 사람에게 넘긴 이유다. 게시도 같은 원칙(중단된 게시는 검토 대기열로)으로 다룬다.
3. **동결된 타입은 값의 조합으로 푼다.** 상태 열거형을 바꾸지 않고, 기존 상태 + 이유 문자열로 새 상황을 표현했다. 계약을 지키면서도 화면과 테스트가 그대로 동작한다.
