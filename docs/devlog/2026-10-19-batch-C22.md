# 2026-10-19 배치 C22: 인스타그램 답글이 새 댓글로 달리던 문제

## 목표

인스타그램 자동 답글이 댓글 아래(스레드 답글)가 아니라 "@작성자 …"로 시작하는 **새 댓글**로 올라갔다. 사용자가 "댓글이 달렸을 때 답글로 다는 게 낫지 않나"라고 물었다. 코드는 이미 "답글 달기"를 누르도록 되어 있어, 왜 새 댓글이 되는지 찾는다.

## 한 일

- **전송 없는 진단**: "답글 달기"를 누르면 입력창에 "@__wo0ong "이 채워지는 것까지 정상이었다. 인스타그램 웹은 "○○님에게 답글 남기는 중" 같은 표시를 따로 보여 주지 않아, 전송 전에는 차이를 볼 수 없었다.
- **실험**: 사용자가 개인 계정으로 테스트 댓글("테스트")을 달아 주었다. 전송 방법만 바꿔 답글을 실제로 보내고, 그 댓글 칸에 "답글 N개"가 늘었는지(스레드) 아니면 글 전체 댓글 수가 늘었는지(새 댓글)로 판정했다.
  - A: 입력창을 다시 클릭하지 않고 한 글자씩 입력 → **답글 0 → 1개(스레드)**
  - D: 입력창을 다시 클릭하지 않고 `insertText` → **답글 1 → 2개(스레드)**
  - 기존 코드: 입력창 클릭 → End → `insertText` → 새 댓글(운영에서 2번 관찰)
  - 결론: `insertText`는 문제가 아니고, **"답글 달기" 뒤 입력창을 마우스로 다시 클릭하는 것**이 답글 대상을 푼다.
- **고침**(`instagram.py` `_REPLY`)
  - 입력창을 클릭하지 않는다. 대신 입력창이 "@작성자"로 시작할 때까지(최대 8초) 기다려 답글 상태를 확인한다.
  - 초점이 입력창에 없을 때만 `focus()`를 부른다(마우스 클릭이 아니라서 답글 대상이 유지된다).
  - 그다음 `insertText`로 이어 쓰고 "게시"를 누른다. 전송 뒤 확인(내 문구 또는 "답글 N개")은 그대로다.
- **테스트**(`tests/unit/test_aside_scripts.py`): 답글 스크립트가 "답글 달기" 뒤에 `box.click()`·`End`를 쓰지 않고, "@작성자" 확인과 `focus()`를 거치는지 구조 검사.
- **문서**: CHANGELOG Fixed, architecture 행, known-gaps(답글 확인 방식).

## 막힌 것과 해결

- **전송 없이 재현할 수 없었다.** 전송 전까지 DOM에 차이가 없다. 그래서 실험마다 실제 답글 1개가 달리는 것을 사용자에게 먼저 알리고, 사용자가 테스트 댓글을 달아 준 뒤 그 아래에만 보냈다. 실험은 2회로 끝냈고 테스트 답글은 지운다.
- **운영 중인 프로그램도 그 댓글을 볼 수 있었다.** 답글 잡이 30분마다 인스타그램 댓글을 읽으므로 테스트 댓글에 먼저 답할 수 있었다. 그 틈을 피해 빠르게 진행했다.
- **왜 클릭이 문제인가.** 인스타그램 웹의 댓글 입력창은 "답글 달기"로 열리면 내부 상태에 "답글 대상"을 기억한다. 입력창을 마우스로 클릭하면 "일반 댓글 쓰기"로 다시 초기화되는 것으로 보인다. 채워진 "@작성자" 글자는 그대로 남아 겉으로는 차이가 없다.

## 배운 것 (신입 개발자용)

1. **겉이 같아도 상태는 다를 수 있다.** 입력창에 "@작성자"가 똑같이 들어 있어도, 한쪽은 "답글", 다른 쪽은 "새 댓글"이었다. 화면 글자가 아니라 애플리케이션의 내부 상태가 결과를 정한다. 그래서 "사람이 하는 것과 같은 동작"을 흉내 낼 때는 불필요한 동작(여기서는 클릭)을 하나라도 더 넣지 않는 것이 안전하다.
2. **변수 하나씩 바꿔 실험한다.** 처음 실험(A)은 두 가지를 동시에 바꿔 성공했다. 어느 것이 원인인지 몰라 한 번 더(D) 했고, 그제서야 "클릭"으로 좁혀졌다. 고칠 때 바꾸는 범위가 작아지고, 왜 고쳤는지 설명할 수 있다.
3. **부작용이 있는 실험은 범위를 정해 알리고 한다.** 운영 계정에 글이 남는 실험이라 횟수(최대 3), 대상(사용자가 만든 테스트 댓글), 뒷정리(삭제)를 먼저 말하고 시작했다.
