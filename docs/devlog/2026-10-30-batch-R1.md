# 2026-10-30 배치 R1: 문서 조각내기와 임베딩 색인

## 목표

"프로젝트 문서를 근거로 답하는 챗봇"(R1 청크·색인 → R2 검색 → R3 대시보드 챗봇)의 첫 단계다. docs의 ADR·devlog·장애 기록·설명서·architecture·contracts·용어집을 조각내고 Gemini 임베딩을 붙여 DuckDB에 저장한다. 검색과 화면은 하지 않는다.

## 한 일

- `nsm/rag/`(신규)
  - `ports.py`: 자체 Protocol `DocumentSource`·`Embedder`(동결된 `nsm/ports/`와 별개, ADR 0056).
  - `chunker.py`: 제목 구조대로 조각. 조각마다 "파일명 > 상위 제목 > 소제목" 경로를 저장하고 본문 첫 줄에 붙인다. 코드 블록은 안 자르고, 큰 표는 행 경계에서 나눠 조각마다 머리글을 다시 붙인다.
  - `sources.py`: docs 폴더 출처(포함·제외 목록).
  - `gemini.py`: `batchEmbedContents` + `outputDimensionality` REST(httpx). 분당 한도면 응답 대기 시간만큼 한 번 기다리고, 하루 한도면 바로 멈춘다. 비용은 `classifier`·ref "embedding".
  - `indexer.py`: 증분 색인 함수 `index_documents`(CLI와 분리, R3의 잡·버튼이 그대로 부름).
  - `command.py`: `nsm index` 몸통. DB 잠금이면 한국어 안내.
- `doc_chunks` 표(스키마 v6), 벡터는 가변 `FLOAT[]`.
- 설정 `settings.rag`: 조각 500자·겹침 80자, 포함·제외 목록, `gemini-embedding-2`·768차원·묶음 100·간격 61초·실행당 900조각·가격(무료 0).
- `nsm index`(`--dry-run`·`--rebuild`·`--stats`·`--db`, 실험용 `--chunk-chars`·`--overlap`·`--docs`).
- `tests/fakes.FakeEmbedder`(결정적 벡터).
- ADR 0056, 설명서 9절 "문서 색인", architecture 6-3절·구현 상태, CHANGELOG. 버전 0.4.14.

## 조각 크기 비교 (실제 docs, 겹침 80자)

| 목표 크기 | 조각 수 | 평균 길이 | 최대 길이 | 제목 단위 중 쪼개진 비율 |
|---|---|---|---|---|
| 300자 | 1,709 | 315자 | 2,869자 | 43% |
| **500자(기본)** | 1,202 | 385자 | 2,869자 | 23% |
| 800자 | 991 | 436자 | 2,869자 | 12% |

(파일 132개, 제목 단위 835개. 길이는 첫 줄 제목 경로를 포함한 글자 수. `nsm index --dry-run --chunk-chars N`)

**500자를 고른 이유.**
- 300자는 제목 단위의 43%가 쪼개진다. "장애 화면 보는 법" 같은 한 절의 설명이 여러 조각으로 흩어져, 검색에서 한 조각만 걸리면 답이 반쪽이 된다. 표 행 하나와 제목 경로만으로도 300자를 넘는 조각이 많다.
- 800자는 쪼개지는 비율이 12%로 낮지만, 대부분의 절이 이미 500자보다 짧아서 평균 길이가 별로 늘지 않는다. 오히려 긴 절에서 여러 주제가 한 벡터에 섞인다.
- 500자는 쪼개진 비율이 23%이고, 길이 대부분이 한 절의 한두 문단에 맞는다. 임베딩 비용은 크기와 거의 무관하다(전체 글자 수가 같음).

## 막힌 것과 해결

- **표 하나가 9,246자 조각이 됐다.** 처음엔 "표·코드는 통째로" 규칙을 그대로 따랐다. 그러자 architecture의 구현 상태 표가 9천 자, ADR 목록이 6천 자, 문제 해결 표가 5천 자짜리 조각이 됐다. 질문 하나에 표 전체가 걸리면 근거가 흐려진다. 표는 행 경계에서만 나누고 조각마다 머리글을 다시 붙였다. 행은 쪼개지 않으니 조각마다 온전한 표다. 최대 조각이 2,869자(contracts의 파이썬 코드 블록)로 줄었다.
- **첫 실제 색인이 12분 넘게 끝나지 않았다.** API는 20개 묶음에 1.6초로 빨랐다. 단계별로 재 보니, DuckDB에 파이썬 리스트(768개)를 매개변수로 넘기는 UPDATE가 행당 약 1초였다(1,179조각이면 20분). 같은 벡터를 "[0.1,…]" 글자로 넘기고 SQL에서 `::FLOAT[]`로 바꾸면 행당 8ms였다. 가짜 768차원으로 전체 색인이 20초가 됐다. 그대로인 파일은 아예 다시 쓰지 않게 해서 두 번째 실행은 0.4초다.
- **무료 구간 한도는 공식 표에 없다.** 실제로 걸려서 429 응답의 한도 이름을 읽었다. 분당 100건·하루 1,000건이고, 묶음 안의 조각 하나하나를 1건으로 센다.
- **재시도가 하루 한도를 태웠다.** 처음 버전은 429마다 기다렸다가 100개 묶음을 다시 보냈다. 저장된 조각은 230여 개뿐인데 하루 한도가 찼다(응답의 대기 시간 51,103초 = 태평양 시간 자정까지). 막힌 시도도 하루 한도에 세어지는 것으로 보인다. 그래서 고쳤다.
  - 하루 한도의 429는 다시 보내지 않고 바로 멈춘다.
  - 분당 한도는 응답의 대기 시간만큼 한 번만 기다린다.
  - 실행당 900조각에서 스스로 멈춘다.
  - 한도는 모델별이라 운영 분류기(`gemini-3.5-flash-lite`)와는 따로다. 운영에는 영향이 없다.
- **Windows의 DuckDB 잠금 문구는 "lock"이 아니다.** 다른 프로세스가 DB를 쥔 상황을 직접 만들어 보니 "File is already open in … (PID …)"였다. 처음 만든 판정("lock" 포함)으로는 놓쳤을 것이다. 두 문구를 다 알아보게 하고, 실제 잠금을 다른 프로세스로 재현하는 테스트를 넣었다.
- **Windows 셸에서 파이썬 문자열의 `\n`이 실제 줄바꿈으로 바뀌어** 파일이 깨지는 일이 두 번 있었다. 파일 쓰기 도구나 `chr(92)`로 고쳤다.

- **코드 리뷰 10건 모두 반영.**
  - ① 차원 설정을 바꿔도 예전 768차원 벡터를 그대로 써 차원이 섞일 뻔했다 → 모델과 함께 차원도 비교해 다르면 다시 임베딩.
  - ② **문서 폴더 경로를 잘못 주면 "모든 파일이 사라짐"으로 보여 색인을 통째로 지웠다** → 문서를 하나도 못 찾았는데 저장된 조각이 있으면 지우지 않고 멈춤, 없는 폴더는 처음에 거부.
  - ③ 설치본에서는 docs 기본 경로가 엉뚱했다 → 소스 폴더에 없으면 지금 폴더의 docs.
  - ④ 겹침이 크기 이상이면 파이썬 오류가 그대로 나왔고 `--chunk-chars 0`은 몰래 기본값이 됐다 → 한국어 안내와 설정 검사.
  - ⑤ 비용 종류가 대시보드에 "자료 분류"로만 보였다 → 표시를 "자료 분류·문서 색인"으로, 0토큰이면 기록 안 함.
  - ⑥ 다른 유료 경로와 달리 하루 비용 상한을 보지 않았다 → 상한이면 임베딩하지 않고 조각만.
  - ⑦ 포함·제외 목록의 "폴더/" 규칙이 서로 달랐다 → 둘 다 docs 맨 위 기준, `*`는 폴더를 넘지 않음.
  - ⑧ 긴 목록을 나눌 때 줄바꿈이 사라졌다 → 줄 단위로 담음.
  - ⑨ 벡터가 빠진 조각이 하나라도 있으면 파일 전체를 매번 다시 썼다 → 내용이 그대로면 그 자리에서 빈 벡터만 채움.
  - ⑩ DB 연결과 HTTP 연결을 닫지 않았다(R3에서 nsm run 안에서 부르면 샘) → 끝나면 닫음.

## 배운 것 (신입 개발자용)

1. **"통째로 두라"는 규칙도 실제 데이터로 재 본다.** 표를 자르지 말라는 건 뜻이 깨지지 말라는 것이었다. 9천 자짜리 표 하나를 한 조각에 넣으면 그 뜻이 오히려 흐려진다. 행 경계에서 머리글을 붙여 나누면 규칙의 목적은 지키고 문제는 피한다.
2. **느릴 때는 짐작하지 말고 단계별로 잰다.** API가 느리다고 생각하기 쉬웠지만, 재 보니 범인은 DB에 리스트를 넘기는 변환이었다. 같은 데이터를 글자로 넘기는 것만으로 100배 넘게 빨라졌다.
3. **재시도는 공짜가 아니다.** 한도에 걸렸을 때 다시 보내면 그 시도도 한도를 쓴다. "분당"이면 기다리면 풀리지만 "하루"면 기다려도 안 풀린다. 오류 응답이 알려 주는 한도 이름과 대기 시간을 읽고, 풀리지 않을 재시도는 하지 않는다.
