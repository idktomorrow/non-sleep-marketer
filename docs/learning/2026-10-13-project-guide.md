# 내가 만든 논슬립 마케터, 팀원의 언어로 다시 이해하기

> 작성: 2026-10-13 · 기준 버전 `v0.3-mvp` · 관련: [architecture.md](../architecture.md) · [adr/](../adr/README.md) · [glossary.md](../glossary.md)
>
> 팀원이 공유한 "디자인 JEV 레퍼런스 기준 제안" 6장을 읽고, 그 틀로 내 프로젝트를 설명해 본 글입니다. 전문용어는 처음 나올 때 한 줄로 풉니다.

## 1. 한 줄로

내 PC에서 돌아가는 AI 직원 한 명입니다. 자료를 읽고 → 글과 카드뉴스를 쓰고 → 인스타그램·스레드에 올리고 → 댓글에 답하고 → 주마다 결산합니다. 위험한 일은 혼자 결정하지 않고 나한테 넘깁니다.

## 2. 이게 무슨 아키텍처인가: 콘센트와 플러그

이름은 **헥사고날 아키텍처**(포트·어댑터 구조)입니다. 어렵게 들리지만 비유 하나면 됩니다.

- **포트** = 콘센트. "글을 써 달라", "이 글이 관련 있는지 판별해 달라", "이걸 올려 달라" 같은 약속의 모양입니다.
- **어댑터** = 플러그. 그 약속을 실제로 해내는 부품입니다. 글쓰기 콘센트에는 Claude 플러그, 판별 콘센트에는 jev 플러그 또는 Claude 플러그, 게시 콘센트에는 Aside 플러그 또는 드라이런(가짜) 플러그가 꽂힙니다.
- **엔진** = 콘센트 모양만 아는 본체. 어떤 플러그가 꽂혔는지 모릅니다.

이 구조 덕분에 실제로 이런 일이 "파일 하나" 수준으로 끝났습니다.

| 바뀐 것 | 어떻게 가능했나 |
|---|---|
| 네이버 블로그 게시 제외 | 설정 기본값 한 줄. 플러그는 그대로 두고 꽂지만 않음 |
| 수집은 Playwright, 게시는 Aside | 브라우저 드라이버를 플러그로 떼어 둬서 설정값으로 선택 |
| jev가 막히면 Claude로 분류 | 같은 콘센트에 플러그 둘. 토큰이 있으면 jev, 없으면 Claude |
| 실제 계정 없이 전체 흐름 테스트 | 게시 콘센트에 "드라이런" 가짜 플러그를 꽂음 |

제미나이나 OpenAI로 바꾸는 것도 "플러그 하나 더 만들기"입니다. 본체는 안 건드립니다.

**한 프로세스 안에 부품 셋**이 있습니다. 스케줄러(알람시계, 7가지 일을 정해진 때에 깨움), 엔진(일꾼. 수집·생성·게시·답글·지표·상태 점검·주간 리포트), 대시보드(사무실 화면, 내 브라우저에서 127.0.0.1:8765). 데이터는 DuckDB 파일 하나에 다 들어 있습니다. 엑셀 파일 하나짜리 데이터베이스라고 보면 됩니다.

흐름을 말로 풀면 이렇습니다.

```
자료 수집(네이버 검색·트렌드·내가 올린 파일)
  → jev가 "관련 있나?" 판별 (0.8 이상만 통과)
  → 주제 분류 → 관련 글만 원문 본문 가져오기
  → Claude가 카드뉴스 덱 + 캡션 + 스레드 글 작성 (모든 주장에 출처 연결)
  → 정책 검사: 출처 없음·금칙어·보호 모드면 검토 대기열, 아니면 승인
  → 승인된 것만 Aside 브라우저가 실제 계정에 게시
  → 5분마다 댓글 수집 → jev가 6가지로 분류 → 답글 / 숨김 / 사람에게
  → 매일 지표 → 월요일 주간 리포트
```

## 3. 팀원 PPT의 틀 ↔ 내 프로젝트

팀원 발표의 핵심은 다섯 가지였습니다. 검색 전에 기준을 정한다, 검색 후 세 번 검증한다, 수집량이 아니라 멈추는 기준을 둔다, jev 판단과 사람 선택을 구분한다, 기준을 문서가 아닌 실행 흐름에 넣는다. 전부 내 프로젝트에 이미 같은 것이 있습니다.

| 팀원 PPT 개념 | 논슬립 마케터에서 같은 것 | 어디에 |
|---|---|---|
| 검색 전 기준: 필수·선호·제외 | 필수 = 페르소나 관심 주제, 선호 = 브랜드 핵심 메시지, 제외 = 후기·여행기·일기·광고 장르를 거르는 정규식 | `nsm/engine/collect.py`, `nsm/domain/quality.py` |
| 검색 후 3단계 검증 | ① 관련성 0.8 이상 ② 주제 분류 ③ 모든 주장에 출처 연결 + 금칙어 검사 | `relevance_threshold`, `policy.decide_publish` |
| 통과·보류·제외 근거 기록 | 콘텐츠 상태 머신: approved / pending_review(사유 문구 포함) / discarded | `nsm/domain/policy.py` |
| 멈추는 기준 (수집량이 아님) | 하루 게시 수(인스타 1·스레드 2), 비용 상한 $3, 같은 사람에게 답글 하루 3회 | 설정(`settings`) |
| JEV 판단 ≠ 사람 선택 | 보호 모드(처음 N건은 사람 승인), 댓글 신뢰도 0.6 미만은 사람에게, 불만·환불·법적 댓글은 무조건 사람에게 | `protect_count`, `MIN_CONFIDENCE` |
| 기준을 실행 흐름에 넣기 | "프롬프트에 적었다"는 "지켜진다"가 아니었음 → 이모지 개수·딱딱한 표현을 코드로 사후 검사하고 1회 재생성 | `quality.py`, ADR 0023 |
| 작은 범위에서 전후 비교 | 드라이런 → 품질 개선(Q1) 전후 원고 비교 → 테스트 계정으로만 실계정 | devlog Q1 |

팀원이 "jev는 판별만 잘하는 모델이라 정확한 목적과 기준을 넣어줘야 한다"고 깨달은 것은, 내 프로젝트에서는 아래 4절처럼 구현되어 있습니다.

## 4. jev에게 실제로 준 기준 (원문)

**자료 관련성** (답은 relevant / irrelevant 둘 중 하나)

> 이 자료가 브랜드 '{브랜드}'({업종})의 SNS 정보 콘텐츠 소재로 쓸 수 있는가? 관심 주제: {주제들}. 관심 주제와 직접 관련된 정보성 글(방법, 기준, 원리, 비교, 정리, 소식)만 relevant다. 주제 낱말이 나와도 방문 후기, 맛집·카페 리뷰, 여행기, 개인 일기·일상 기록, 구매·사용 후기, 광고 홍보 글은 irrelevant다.

처음 드라이런에서는 이 문장이 더 느슨해서 "후쿠오카 카페 방문 후기"가 0.93으로 통과했습니다. 기준을 문장으로 정확히 적고, 그 앞에 정규식 필터까지 두자 걸러졌습니다. 팀원이 말한 "모호한 요청 → 검색 브리프로 바꾸기"가 바로 이것입니다.

**댓글 6분류**

> SNS 게시물에 달린 댓글을 분류하라. praise_general=칭찬·일반 반응, question=질문, complaint=불만, price_refund=가격·환불·결제 문의, legal=법적 문제·권리 침해 주장, spam=광고·홍보·사기성 링크.

**기준값**

| 값 | 뜻 |
|---|---|
| 0.8 | 관련성이 이 미만이면 자료로 쓰지 않음 |
| 0.6 | 댓글 분류 신뢰도가 이 미만이면 사람에게 |
| 20건 (이 PC는 10건) | 보호 모드. 사람 승인이 이만큼 쌓이기 전에는 자동 게시 안 함 |
| $3 | 하루 비용 상한. 넘으면 생성 중단 |
| 3회 | 같은 사람에게 하루 답글 상한 |

jev의 신뢰도는 "1등과 2등 확률의 차이"라서 그대로 쓰면 관련 자료가 거의 다 떨어졌습니다. 고른 라벨의 확률로 바꿔 읽도록 고쳤습니다. 판별 모델도 출력값의 뜻을 확인해야 한다는 교훈입니다.

## 5. 왜 이렇게 만들었나: ADR 29건 중 꼭 알 10건

ADR은 "설계 결정 하나를 적은 문서"입니다. 왜 그렇게 했는지가 적혀 있어서, 나중에 뒤집을 때도 이유를 압니다.

| 번호 | 결정 | 한 줄 이유 |
|---|---|---|
| 0001 | 공식 API 대신 로그인된 브라우저 자동화 | 공식 API는 승인 절차가 길고 제약이 큼. 제재 위험은 테스트 계정으로 감수 |
| 0002 | 브라우저 드라이버를 플러그로 분리 | Aside가 안 되면 Playwright로, 파일 하나만 바꿔서 |
| 0003 | 분류는 jev 기본 + Claude 동등 구현 | jev는 프리뷰라 막힐 수 있음. 설정 한 줄로 전환 |
| 0005 | 드라이런부터 | 계정 없이 전체 흐름을 먼저 검증 |
| 0006 | 단일 프로세스 + DuckDB + FastAPI | DuckDB는 한 프로세스만 열 수 있어 Streamlit을 버림 |
| 0007 | 표기 강제, 후기형 템플릿 금지 | 가상인물이 "직접 써 봤다"고 쓰면 공정위 지침 위반 소지 |
| 0008 | 자동 게시 가드레일 | 보호 모드·쿼터·비용 상한·출처 검사를 전부 통과해야 자동 게시 |
| 0016 | 네이버 블로그 게시 제외 | 범위를 줄이되 수집 소스로는 유지 |
| 0021 | 수집은 Playwright, 게시만 Aside | 수집은 로그인 불필요. 내 브라우저에 탭이 열리는 불편 회피 |
| 0023 | 셀 수 있는 규칙은 코드로 검사 | 프롬프트에 적은 규칙은 어겨도 통과됐음 |

## 6. "모든 자동화는 허상"에 대한 내 프로젝트의 답

팀원 말이 맞습니다. 내 프로젝트도 전부 자동이 아닙니다. 원칙은 하나였습니다. **잘못돼도 되돌릴 수 있는 일만 자동으로 한다.**

| 자동 | 사람 |
|---|---|
| 자료 수집·판별 | 브랜드·페르소나·관심 주제 설정 |
| 원고·카드 생성 | 처음 N건 승인 (보호 모드) |
| 승인된 글 게시 | 출처 없음·금칙어 걸린 글 검토 |
| 칭찬·질문 댓글 답글, 스팸 숨김 | 불만·환불·법적 댓글 처리 |
| 지표 수집, 주간 리포트 계산 | 카드 문구·배경 편집, 리포트 읽고 주제 조정 |

삭제처럼 되돌릴 수 없는 동작은 아예 안 합니다. 인스타그램은 댓글 숨기기가 없어서 스팸도 사람에게 넘깁니다.

## 7. "DB에 쌓인 것 중 무엇이 좋은가를 AI가 고르게 하려면"

내 프로젝트의 답은 세 겹입니다.

1. **기준을 먼저 숫자로 만든다.** 관련성 0.8, 출처 연결 여부, 금칙어. 이건 jev와 코드가 자동으로 봅니다.
2. **사람의 선택을 데이터로 남긴다.** 내가 승인한 건수(`human_approved`), 폐기한 사유가 DB에 남습니다. 보호 모드 해제 여부가 여기서 결정됩니다.
3. **결과로 사후 평가한다.** 주간 리포트가 참여율(좋아요+댓글+저장+공유 ÷ 조회)로 최고 성과 글과 추천 주제를 뽑습니다. 이건 LLM 없이 규칙으로 계산해서 같은 데이터면 늘 같은 답이 나옵니다.

팀원 프로젝트(디자인 레퍼런스)에 옮기면 이렇게 말할 수 있습니다. 필수 기준(화면 종류·기기·제외 조건)은 필터로 거르고, 선호 기준(다크톤·절제됨)은 jev의 선택형 질문으로 "둘 중 어느 쪽이 더 절제됐나"를 쌍대 비교해 순위를 매기고, 사람이 최종으로 고른 것과 고르지 않은 이유를 저장해 다음 추천의 근거로 되먹임한다. 1,000개를 모으는 대신 "결정에 쓰인 자료의 비율"을 지표로 본다.

## 8. 팀원과 이야기할 때 준비할 것

**물어볼 것 5개**

1. 필수·선호·제외 조건은 누가, 어느 화면에서 입력하나요? 매 작업마다인가요, 한 번 정해 두나요?
2. "보류"로 간 자료는 누가 언제 다시 보나요? 쌓이기만 하면 사실상 제외와 같아집니다.
3. 멈추는 기준의 첫 실험값은 무엇으로 시작할 건가요? (예: 유효 비율 30% 이하로 떨어지면 중단)
4. Claude가 화면 이미지를 보는 단계는 비용이 큰데, 건당 상한이나 하루 상한이 있나요?
5. 사람이 고른 결과를 다음 검색에 어떻게 되먹임하나요?

**보여 줄 수 있는 내 실물 3개**

- 검토 대기열의 사유 문구("자료 관련성 0.62 < 0.80", "출처 없는 주장") → 팀원이 말한 "통과·보류·제외 근거 표시"의 실제 예
- 주간 리포트 화면 → "선택·재사용" 지표의 실제 예
- Q1 품질 개선 devlog의 전후 원고 비교 → "작은 범위 전후 비교"의 실제 예

## 9. 용어 15개

| 용어 | 한 줄 | 비유 |
|---|---|---|
| 포트 / 어댑터 | 약속의 모양 / 그 약속을 해내는 부품 | 콘센트 / 플러그 |
| 드라이버 | 브라우저를 직접 조작하는 층 | 운전기사 |
| 드라이런 | 실제로 올리지 않고 결과만 폴더에 저장 | 리허설 |
| 잡(job) | 스케줄러가 정해진 때에 돌리는 일 | 알람에 묶인 할 일 |
| 상태 머신 | 허용된 상태 변화만 가능 | 신호등 순서 |
| 멱등성 | 두 번 해도 한 번 한 결과와 같음 | 엘리베이터 버튼 두 번 누르기 |
| claim | 사실 주장과 그 출처의 짝 | 각주 달린 문장 |
| 보호 모드 | 처음 N건은 사람이 승인 | 수습 기간 |
| 쿼터 | 하루 최대 허용 횟수 | 일일 한도 |
| jev | 선택지 중 하나를 확률과 함께 고르는 판별 전용 모델 | 심사위원 |
| DuckDB | 파일 하나로 쓰는 무료 DB | 엑셀 파일 하나짜리 DB |
| keyring | 비밀 키를 OS 자격 증명 저장소에 보관 | 금고 |
| 지터 | 봇처럼 보이지 않게 섞는 무작위 지연 | 출근 시간 ±10분 |
| capability | 어댑터가 할 수 있는 일 목록 | 메뉴판 |
