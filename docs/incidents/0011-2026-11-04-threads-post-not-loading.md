# 0011. 스레드 글 페이지가 열리지 않는데 13시간 "새 댓글 없음"(정상)으로 보임

- 날짜: 2026-11-04 (06:42부터, KST. 21:26 확인까지 계속, 회복 전)
- 종류(ADR 0054): `transient`여야 했는데 표 밖(예외 없는 조용한 빈 결과)으로 지나감
- 고친 것: 배치 C37, ADR 0062

## 증상 (사용자가 본 것)

- 스레드 글 페이지를 직접 열어 보니 본문 자리에 로딩 표시만 돌다가 "문제가 발생했습니다. 나중에 다시 시도해보세요." 안내와 "다시 시도" 버튼이 떴다.
- 대시보드는 아무 문제도 없어 보였다. 실행 기록은 모두 "새 댓글 없음"이었고, 장애 화면의 스레드는 "정상"이었다. 알림도 없었다.
- 증거 `threads-20261104-192259`의 스크린샷은 왼쪽 메뉴와 오른쪽 인사이트(조회 24회)만 그려지고, 가운데 본문 자리에 로딩 표시만 있다.

## 원인

- **겉으로 보인 것**: "새 댓글 없음". 오류가 아니라 성공으로 기록됐다.
- **우리 쪽 원인(확정)**: `_COMMENTS`는 글마다 `nsmUntil(..., 20000)`으로 댓글 칸을 기다린다. `nsmUntil`은 시간이 지나면 null을 돌려줄 뿐 던지지 않는다. 그래서 본문이 안 뜬 글도 "댓글 0개"로 넘어갔다. 36개 글마다 20초 넘게 기다려 한 번이 14분이 됐고, 결과는 빈 목록이었다.
- **스레드 쪽 원인(확정: 우리 계정에 걸린 제한)**: 2026-11-04 밤 사용자가 직접 가려냈다.
  - 같은 컴퓨터에서 다른 계정으로는 우리 글과 댓글이 열렸고, 논슬립마케터 계정으로 바꾸면 "나중에 다시 시도"가 떴다.
  - 다른 사람 글은 우리 계정으로도 열렸다.
  - 다른 컴퓨터에서도 같았다.
  - 따라서 IP나 스레드 장애가 아니라 **우리 계정에 걸린 제한**이고, 막힌 것은 **우리 계정이 자기 글 페이지를 여는 동작**뿐이었다. 게시·인사이트·프로필은 정상이었고, 글은 남들에게 보였다.
- **제한이 걸린 까닭(추정)**: 자동화 패턴으로 추정한다. 5분마다 최근 14일 글 36개를 열어, 하루 약 9,360번 자기 글 페이지를 열었다. 메타가 공식적으로 알려 준 것은 없다.
- **조치**:
  - 11-04 밤 스레드 댓글 확인 간격을 180분, 최근 일수를 1일로 낮췄다.
  - 회복 시각: 아직 회복 전(2026-11-04 21:26 확인까지 "플랫폼이 오류 화면을 띄움", 기록 시점 21:46). 회복되면 날짜와 시각을 여기에 적는다.
  - 회복 뒤 15분·7일로 되돌린다.

## 어떻게 발견했나

사용자가 스레드 글을 직접 열어 보고 알았다. 앱의 실행 기록·장애 화면·알림으로는 드러나지 않았다.

## 고친 것

배치 C37, ADR 0062.

- **오류 화면 감지**: "문제가 발생했습니다 / Something went wrong / 나중에 다시 시도 / Try again later" 안내문과 "다시 시도" 버튼이 함께 있으면 `page` 오류(일시적)로 던진다. 버튼이 함께여야 해서 댓글에 같은 말이 있어도 걸리지 않는다. 로그인 확인보다 먼저 보므로 E5의 빈 화면 판정보다 앞선다.
- **조용한 빈 결과 금지**: 글 본문처럼 반드시 있어야 하는 요소를 기다린 결과가 비면 `nsmEnsure`가 오류 화면을 한 번 더 보고, 아니면 "게시물 본문이 20초 안에 열리지 않음"으로 던진다. 본문은 떴는데 댓글이 없는 글만 빈 목록이다.
- **연속 실패 시 쉬기**: 같은 플랫폼의 댓글 조회가 일시적 오류로 연속 2번 실패하면 그 플랫폼 댓글 확인만 30분 쉬고, 그 연속 구간에 한 번 알린다("스레드 게시물이 열리지 않아 댓글 확인을 30분 쉽니다"). 게시는 그대로 한다.
- **덜 열기**: 스레드 댓글 확인 간격 15분(설정), 최근 글 7일(14일에서 낮춤). 하루 약 9,360번 → 최대 960번(96회 × 10개).
- **소요 시간 경고**: 댓글 확인이 잡 간격의 2배를 넘게 걸리면 실행 기록과 장애 화면 실패 목록에 "댓글 확인이 N분 걸림(간격 M분)"을 남긴다(알림 없음).

## 재발 방지

- 테스트(`tests/unit/test_page_errors.py`)는 실제 스크립트를 node에서 가짜 화면에 대고 돌린다. 오류 화면, 본문 없이 시간 초과, 본문은 있고 댓글 0개, 댓글 속 같은 문구를 각각 고정했다.
- `nsmUntil`을 쓰는 34곳을 하나씩 판단해 devlog에 표로 남겼다(`docs/devlog/2026-11-04-batch-C37.md`). 새 스크립트에서 반드시 있어야 하는 요소는 `nsmEnsure`로 감싼다.
- 기준은 자기 글 페이지를 여는 횟수다. 새 기본값(15분·7일, 하루 최대 960번)으로도 되풀이되면 간격을 더 늘린다.
- 남은 위험: 플랫폼이 오류 안내문 문구를 바꾸면 감지가 빠진다. 그래도 본문 시간 초과로 같은 오류가 난다(늦게 알 뿐 조용하지는 않다).

## 지금 체계였다면

E1~E5 아래에서 일어난 장애다. 실제로는 이렇게 보였다.

- **E1(오류 종류 표)**: 예외가 없어서 표가 쓰일 기회가 없었다. 증거도 19:22 "탭이 닫히지 않음" 오류 때 처음 남았다.
- **E2(장애 화면)**: 스레드는 "정상"으로 보였다.
- **E5(빈 화면 판정)**: 로그인 확인 단계의 빈 화면만 다루고, 글 본문을 기다리는 단계는 다루지 않았다.
- **감시(ADR 0041)**: "계속 0건" 감시는 수집·게시만 봤다. 댓글 0건은 흔한 일이라 감시 대상이 아니었다.
- **배운 점**: 기다리기가 "못 찾음"을 값으로 돌려주면, 부르는 쪽이 꼭 그 값을 확인해야 한다. 확인하지 않은 곳에서는 실패가 성공으로 바뀐다.
